sudo xcodebuild -license accept

A·B보다 먼저 할 필요는 없습니다. 업로드 전까지만 해 두시면 됩니다.

A. App Store 프로비저닝 프로파일

프로비저닝 프로파일은 "이 팀의 이 인증서로 서명한 이 앱(com.begreen.greenday)을 App Store에 올려도 된다"는 Apple의 허가증입니다. 인증서는 이 맥에 이미 다 있고(Apple Distribution: MINSEOK SHIN, 2027-07-30까지 유효), App ID도 이미 등록돼 있어서 프로파일 하나만 새로 만들면 됩니다.

A1

옛 haru 항목 정리 (먼저)

Identifiers 목록에 이름이 "Greenday"인 항목이 둘이라, 다음 단계 드롭다운에서 잘못 고르기 쉽습니다. 옛 것을 먼저 치웁니다. 순서가 중요합니다: 프로파일을 먼저, App ID를 나중에.

  1. developer.apple.com → Profiles에서 App ID가 com.supaicy.haru인 프로파일(이름 haru MAS)을 클릭 → Remove(또는 Delete).
  2. Identifiers에서 Identifier가 com.supaicy.haru인 항목 클릭 → 맨 아래 Remove.
BicMac(com.supaicy.bicmac)은 건드리지 마세요. 별개 앱입니다. 지운 Identifier는 다시 등록할 수 없지만 com.supaicy.haru는 배포된 적이 없고 다시 쓸 일도 없습니다.

이 단계를 건너뛰고 싶다면, 옛 App ID를 클릭해 Description만 Greenday (OLD — do not use)로 바꿔 두는 것도 됩니다. 핵심은 다음 단계에서 헷갈리지 않는 것입니다.

A2

프로파일 만들기

  1. Profiles → ＋(새 프로파일)을 엽니다.
  2. Distribution 묶음에서 Mac App Store Connect를 고르고 Continue. (위쪽 Development 묶음이나 "App Store Connect"(iOS)가 아닙니다. 이름에 Mac이 들어간 것입니다.)
  3. App ID 드롭다운에서 Greenday (32R6RHXU36.com.begreen.greenday)를 고릅니다. 괄호 안이 com.begreen.greenday인지 꼭 확인하세요. → Continue.
  4. Certificates에서 Apple Distribution: MINSEOK SHIN(만료 2027/07/30)을 체크 → Continue. (같은 이름이 여러 개면 만료일이 2027/07/30인 것. 그게 이 맥에 깔린 인증서입니다.)
  5. Provisioning Profile Name에 Greenday Mac App Store → Generate.
  6. Download. 다운로드 폴더에 Greenday_Mac_App_Store.provisionprofile 같은 파일이 생깁니다. 더블클릭하지 않아도 됩니다.

App ID에서 따로 켤 기능(Capabilities)은 없습니다. 이 앱의 샌드박스 권한은 네트워크·사용자가 고른 파일뿐이라 App ID 설정이 필요 없습니다.

A3

정해진 자리에 저장

터미널에 붙여넣으세요. 다운로드 폴더의 프로파일을 저장소의 정해진 이름으로 옮깁니다.

mv ~/Downloads/*.provisionprofile ~/Code/services/greenDay/resources/embedded.provisionprofile

다운로드 폴더에 .provisionprofile이 둘 이상 있으면 이 명령이 실패합니다. 그때는 파일 이름을 직접 적어 주세요. 이 파일은 .gitignore에 들어 있어 저장소(GitHub)에는 올라가지 않습니다.

A4

확인 (선택)

직접 확인하고 싶으면 아래를 돌리세요. 안 돌리고 "프로파일 넣었어"라고만 말해 주셔도 제가 돌립니다.

cd ~/Code/services/greenDay && npm run mas:preflight
이렇게 나오면 성공 — 2/6 프로비저닝 프로파일 아래에
  • ✓ 프로파일 App ID 일치: 32R6RHXU36.com.begreen.greenday
  • ✓ 플랫폼: macOS · ✓ 팀: 32R6RHXU36 · ✓ 만료: (1년 뒤 날짜)

6/6의 Google 클라이언트 ID 항목은 B를 마칠 때까지 ✗가 정상입니다.

프로파일이 다른 앱의 것입니다 → A2-3에서 App ID를 잘못 골랐습니다. 그 프로파일을 지우고 A2를 다시.
macOS용 프로파일이 아닙니다 → A2-2에서 iOS용 "App Store Connect"를 골랐습니다. "Mac App Store Connect"로 다시.
프로파일을 읽지 못했습니다 → 다운로드가 덜 됐거나 다른 파일입니다. 다시 Download.
A2-4에서 인증서가 목록에 없음 → 그 화면을 캡처해서 보여 주세요. 인증서를 새로 만들 필요가 있는지 제가 판단합니다.

B. Google 캘린더 연동 — OAuth 클라이언트 ID

Google 캘린더 동기화는 사용자가 "Google로 연결"을 누르면 브라우저에서 로그인하고, 앱이 그 계정에 Greenday라는 별도 캘린더를 하나 만들어 거기에만 일정을 씁니다. 사용자의 기존 캘린더는 목록조차 보지 않습니다. 이 로그인 창구를 Google에 등록하는 것이 이 절입니다. 클라이언트 ID는 비밀이 아니고 빌드할 때 앱 안에 들어갑니다.

Google 콘솔은 2025년에 OAuth 화면을 Google 인증 플랫폼(영문 Google Auth Platform)으로 재편했습니다. 메뉴 이름이 아래와 조금 다르면 가장 가까운 것을 고르고, 막히면 화면을 캡처해 보여 주세요.

B1

프로젝트 만들기

  1. console.cloud.google.com → 새 프로젝트.
  2. 프로젝트 이름 Greenday → 만들기. 만들어지면 위쪽 프로젝트 선택기에서 Greenday가 골라져 있는지 확인합니다.
B2

Google Calendar API 켜기

  1. API 라이브러리 → Google Calendar API.
  2. 사용(Enable). 이미 "API 사용 설정됨"이면 그대로 둡니다.
B3

Google 인증 플랫폼 → 개요에서 시작하기를 누르면 네 단계 마법사가 나옵니다.

B5

데이터 액세스 — 범위 하나 추가

  1. 왼쪽 메뉴 데이터 액세스(Data Access) → 범위 추가 또는 삭제.
  2. 패널 아래쪽 직접 범위 추가 칸에 아래를 붙여넣고 표에 추가 → 업데이트.
https://www.googleapis.com/auth/calendar.app.created
  1. 화면 아래 저장.
여기서 하나만 봐 주세요. 추가된 범위가 "민감하지 않은 범위" 표에 들어갔는지, "민감한 범위" 표에 들어갔는지. 저장소 문서는 민감하지 않다고 적고 있지만 Google 공식 문서에서는 확인되지 않았습니다. Google 화면이 정답이니, 어느 쪽인지 클라이언트 ID와 함께 알려 주세요.
  • 민감하지 않음 → 심사 없이 B7에서 바로 게시할 수 있습니다.
  • 민감함 → 게시하려면 Google 앱 인증(설명 영상·사용 이유 작성, 보통 수 일~수 주)이 필요합니다. 그 준비물은 제가 따로 정리해 드립니다.
B6

클라이언트 만들기 — 이게 전달할 값

  1. 왼쪽 메뉴 클라이언트(Clients) → 클라이언트 만들기.
  2. 애플리케이션 유형: 데스크톱 앱. (iOS·Android·웹 애플리케이션이 아닙니다. 번들 ID나 리디렉션 URI를 묻는 칸이 나오면 유형을 잘못 고른 것입니다.)
  3. 이름: Greenday macOS → 만들기.
  4. 뜨는 창의 클라이언트 ID를 복사합니다. 모양은 이렇습니다.
123456789012-abcdefghijklmnopqrstuvwxyz012345.apps.googleusercontent.com

같은 창의 클라이언트 보안 비밀(GOCSPX-…)과 JSON 다운로드는 무시하세요. 앱은 PKCE 방식이라 보안 비밀을 쓰지 않습니다. 클라이언트 ID는 나중에도 클라이언트 목록에서 다시 볼 수 있습니다.

B7

대상 — 테스트 사용자 추가, 그리고 출시 전 게시

  1. 왼쪽 메뉴 대상(Audience) → 테스트 사용자 → Add users → 당신의 Gmail 주소 → 저장. 지금은 게시 상태가 테스트라서, 이 목록에 있는 계정만 로그인됩니다. 제가 TestFlight 빌드로 연결을 확인할 때 이 계정을 씁니다.
  2. 출시 직전에 같은 화면의 앱 게시(Publish app)를 눌러 프로덕션으로 바꿉니다. 그 전에는 아무도 연결할 수 없습니다.
테스트 상태로 출시하면 안 되는 이유. 테스트 상태의 외부 앱이 받는 리프레시 토큰은 7일 뒤 만료됩니다. 테스트 사용자도 일주일마다 다시 로그인해야 하고, 목록에 없는 사람은 아예 연결되지 않습니다. App Store 심사에 내기 전에 게시하라고 제가 그때 다시 알려 드립니다.
B8

전달

Google 클라이언트 ID: 123456789012-…….apps.googleusercontent.com

GitHub Actions 자동 릴리스를 쓸 거라면 이 값을 저장소 Settings → Secrets → Actions에 GOOGLE_OAUTH_CLIENT_ID로도 넣어야 합니다. 로컬 릴리스만 하면 필요 없습니다.
