haru · 배포 설정

첫 배포까지 — 지금 하실 일은 두 가지

Apple 개발자 계정 결제와 인증서 발급은 끝났습니다. 남은 건 앱 암호 발급과 맥에 한 번 저장, 이 둘뿐입니다. 5분이면 끝납니다.

궁금해하신 것에 대한 답

질문답
내가 뭘 해야 해?앱 암호 만들기 → 맥에 한 번 저장하기. 그게 전부입니다
GitHub 시크릿은 왜 등록해?이제 안 하셔도 됩니다. 사장님 맥에서 직접 배포하기로 했으니까요
인증서 내보내기는 왜 해?안 하셔도 됩니다. 도장이 이미 이 맥에 있고, 여기서 빌드하니까요
새 앱 암호를 만들어야 해?네, 하나. 이 방식에서 Apple에 로그인하는 수단이 그겁니다
앞서 GitHub 시크릿 6개와 인증서 내보내기를 안내드렸던 건 GitHub에서 자동으로 빌드하는 경우였습니다. 맥에서 직접 하기로 정하셨으니 그 준비는 전부 불필요해졌습니다.

왜 이런 구조인가

핵심은 하나입니다. 앱을 어느 컴퓨터에서 만드느냐.

[ GitHub에서 빌드 ]                    [ 내 맥에서 빌드 ]  ← 선택하신 방식

  깨끗한 새 맥을 빌려 씀                  이미 쓰던 내 맥
  도장 없음  → 복사해 보내야 함            도장 이미 있음  ✔
  Apple 로그인 없음 → 키 보내야 함         로그인만 한 번 저장하면 끝

  준비: 인증서 내보내기 + 시크릿 6개       준비: 앱 암호 1개
  이후: git tag 하나로 자동                이후: npm run release

"인증서 내보내기"는 맥 Keychain 안에 잠겨 있는 도장을 파일로 꺼내 다른 컴퓨터가 쓸 수 있게 하는 작업이었습니다. 같은 맥에서 빌드하면 꺼낼 이유가 없습니다.

하실 일

1

앱 암호 발급 (웹, 2분)

account.apple.com 로그인 → 로그인 및 보안 → 앱 암호 → +

이름은 자유롭게, 예: haru 공증

abcd-efgh-ijkl-mnop 형태 16자가 나옵니다.

이 창을 닫으면 다시 볼 수 없습니다. 바로 다음 단계에 붙여넣으세요. 그리고 다른 세션에서 만든 앱 암호는 그대로 두세요 — 섞어 쓰면 하나를 폐기할 때 둘 다 죽습니다.
2

맥에 한 번 저장 (터미널, 1분)

xcrun notarytool store-credentials "haru" \
  --apple-id <사장님 Apple ID> \
  --team-id 32R6RHXU36 \
  --password <방금 받은 앱 암호>

팀 ID 32R6RHXU36은 인증서에서 확인된 값이라 그대로 쓰시면 됩니다. 이걸로 앱 암호가 Keychain에 들어가고 앞으로 다시 입력할 일이 없습니다.

셸 히스토리에 남기지 않으려면 명령 맨 앞에 공백 한 칸을 넣고 실행하세요.

그 다음 — 배포

npm run release

이 한 줄이 아래를 순서대로 합니다.

1/4  사전 확인 ──┬── Developer ID 인증서가 Keychain에 있는가
                 ├── 공증 자격증명 "haru" 가 유효한가
                 └── GitHub 토큰이 있는가
                        │
                        └─ 하나라도 없으면 여기서 중단 ✋

2/4  빌드        electron-vite build

3/4  패키징      서명 → 공증 → GitHub draft 릴리스 게시
                 (arm64 + x64 dmg)

4/4  검증        codesign --verify
                 spctl → "Notarized Developer ID" 확인
                        │
                        └─ 실패하면 draft로 남김 (사용자에게 안 나감) ✋

완료 → 공개 명령어를 알려줍니다
이 안전장치가 왜 필요한가. electron-builder는 공증 자격증명이 없으면 조용히 건너뛰고 성공한 척 합니다 (macPackager.js: "if no credentials provided, skip silently"). 그대로 나가면 사용자가 다운로드해서 열 때 "손상되었거나 열 수 없습니다"를 만납니다. 개발자는 성공했다고 믿고 있는데 사용자만 아는 실패입니다. 그래서 앞뒤로 두 번 확인합니다.

공개하기

npm run release가 끝나면 릴리스가 draft로 올라갑니다. 확인 후 공개하세요.

gh release edit v2.0.1 --draft=false --latest

공개하는 순간 Homebrew cask도 자동 갱신돼서 brew upgrade haru 쓰는 분들에게도 나갑니다.

이게 v1.4.1(2026-04-20) 이후 3개월 만의 첫 배포입니다. CHANGELOG에 "첫 정식 공개 릴리스"라고 적힌 v2.0.0은 실제로는 GitHub에 올라간 적이 없습니다.

나중에 자동화하고 싶어지면

GitHub Actions 워크플로는 이미 준비돼 있습니다(커밋 fe700b0). 그때는 인증서를 .p12로 내보내고 App Store Connect API 키를 발급해 시크릿 6개를 등록하면, 이후로는 git tag 하나로 전부 자동입니다.

지금은 그 워크플로가 시크릿이 없으면 Preflight에서 멈추도록 해뒀습니다. 로컬 배포에는 방해가 안 되고, 실수로 태그를 밀었을 때 서명 없는 dmg가 나가는 걸 막아줍니다.
