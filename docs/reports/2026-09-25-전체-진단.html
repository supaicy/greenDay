2.1 할일 제목에 constructor를 치면 앱 전체가 백지가 된다

src/renderer/src/utils/naturalDate.ts:298 (같은 모양이 283·290·343·350·358에도)

DAY_MAP·EN_DAY_MAP이 평범한 객체 리터럴이라 Object.prototype을 상속합니다. DAY_MAP['constructor']는 undefined가 아니라 함수를 돌려주므로 !== undefined 가드를 통과하고, 그 값이 곧바로 배열 인덱스로 쓰여 NEXT_DAY_FN[<함수>](today) → undefined(...)가 됩니다.

자연어 날짜 파싱은 AddTask·QuickAdd의 useEffect에서 글자를 칠 때마다 돕니다. 제출도 필요 없습니다. 그리고 렌더러 어디에도 ErrorBoundary가 없어(2.3) React가 루트를 통째로 언마운트합니다.

실측 — Cmd+N 후 "constructor buy milk" 타이핑 BEFORE: {"root":1,"buttons":54,"len":1023} AFTER : {"root":0,"buttons":0,"len":0} uncaught TypeError: Gr[p] is not a function 프로브 — Object.prototype 키 12개 전부 크래시(단독·구문 선두·한글 접두사 모두) constructor, toString, valueOf, hasOwnProperty, isPrototypeOf, propertyIsEnumerable, toLocaleString, __proto__, __defineGetter__, __defineSetter__, __lookupGetter__, __lookupSetter__ 생존: 0개

고치기: 6개 지점 전부 Object.hasOwn(DAY_MAP, text)로 가드하거나, 맵을 Object.create(null)/Map으로 선언합니다.

2.2 UTC 서쪽에서는 모든 날짜가 하루 밀린다

src/renderer/src/utils/date.ts:29 (48·54·59·64·79도 같음)

날짜를 쓸 때는 로컬 기준 toLocalDateString을 쓰는데, 읽을 때는 new Date('YYYY-MM-DD')를 씁니다. 후자는 ECMAScript 규격상 UTC 자정으로 해석됩니다. 오프셋이 음수인 지역에서는 두 기준이 하루 어긋납니다.

실측 — 같은 코드, 시간대만 바꿔가며 (오늘 = 로컬 기준 오늘) Asia/Seoul (+9) isToday=true OK UTC ( 0) isToday=true OK Europe/London (+1) isToday=true OK America/New_York(-4) isToday=false isYesterday=true isOverdue=true ← 틀림 America/LA (-7) isToday=false isYesterday=true isOverdue=true ← 틀림 Pacific/Honolulu(-10) isToday=false isYesterday=true isOverdue=true ← 틀림

미주 사용자에게 오늘 마감인 할일이 "어제"로 뜨고 연체로 표시됩니다. 내일 마감은 "오늘"로 뜹니다. '내일'·'다음 7일' 스마트 리스트도 하루씩 밀립니다.

왜 테스트가 못 잡았는가: vitest.config.ts가 TZ: 'Asia/Seoul'로 고정돼 있습니다. 주석은 "UTC 머신에서 회귀 테스트가 통과해버리는 것"을 막으려는 의도라고 적혀 있는데, UTC+9로 고정하면 반대쪽(음수 오프셋) 케이스가 통째로 가려집니다.

고치기: fromLocalDateString(s) 헬퍼를 toLocalDateString 옆에 두고 date.ts의 모든 new Date(dateStr)를 교체합니다. 그리고 날짜 테스트를 음수 오프셋 시간대에서도 한 번 더 돌리는 프로젝트를 추가해야 재발을 막습니다.

2.3 ErrorBoundary가 없어, 렌더 예외 한 번이 앱을 영구히 백지로 만든다

src/renderer/src/ 전역 — componentDidCatch/getDerivedStateFromError/ErrorBoundary 검색 결과 0건

2.1은 타이핑 중 크래시라 재시작하면 살아납니다. 하지만 나쁜 값이 디스크에 저장되는 경로라면 재시작해도 같은 자리에서 다시 죽습니다. 실제로 그 상태를 만들어 확인했습니다.

실측 — tags가 배열로 파싱되지 않는 행 1개가 DB에 있을 때 reload 후: root=0 buttons=0 bodyLen=0 (창은 열리지만 완전히 빈 화면) uncaught TypeError: a.tags.map is not a function → 데이터가 디스크에 있으므로 재시작해도 동일. 앱 안에서 복구할 방법 없음.

연결된 검증 공백이 둘 있습니다. validate.ts는 pinned·날짜·scheduledOverrides는 검사하면서 tags·attachments는 검사하지 않고, updateTask는 받은 값을 그대로 JSON.stringify합니다. 렌더러의 safeParseJson<string[]>은 파싱 결과를 as로 캐스팅만 할 뿐 배열인지 확인하지 않습니다.

공정하게: 제가 이 상태를 만든 경로는 IPC에 직접 문자열을 넣은 것이라 일반 사용자의 평소 조작은 아닙니다. LLM이 만든 tags는 sanitizeTaskResult가 Array.isArray로 제대로 막고 있습니다. 문제는 트리거보다 결과입니다 — 어떤 렌더 예외든 결과가 "앱 영구 백지"입니다.

고치기: 루트에 ErrorBoundary를 두어 백지 대신 복구 화면(데이터 내보내기·해당 항목 건너뛰기)을 보여 줍니다. safeParseJson에 형태 검증을 붙이고, validate.ts에 tags/attachments 타입 검사를 추가합니다.

2.4 Caps Lock이 켜져 있으면 단축키 5개가 통째로 죽는다

src/renderer/src/hooks/useKeyboardShortcuts.ts:83·88·96·102·110

핸들러가 key === 'n'처럼 소문자만 비교합니다. Caps Lock이 켜지면 e.key가 'N'이 되어 전부 무시됩니다. Cmd+Shift+A만 (key === 'a' || key === 'A')로 양쪽을 처리하는데, 그 예외가 나머지로 일반화되지 않았습니다.

실측 — 실제 키 이벤트 전송 Cmd+n → 할일 추가 입력창 열림·포커스 OK Cmd+N → 아무 일도 없음 (focus: BODY) 죽음 Cmd+f → 검색창 포커스 OK Cmd+F → 포커스 안 됨 죽음 실측 — 삭제 후 되돌리기 (가장 아픈 경로) 할일 삭제 → tasks 25, trash 1 Cmd+Z (Caps) → tasks 25, trash 1 되돌아오지 않음 Cmd+z → tasks 26, trash 0 되돌아옴

영향받는 단축키: Cmd+N(추가) · Cmd+F(검색) · Cmd+Z(되돌리기) · Cmd+E(내보내기) · Cmd+D(오늘 마감). 설정 화면이 이 단축키들을 광고하고 있어서 사용자는 "앱이 고장났다"고 느낍니다.

고치기: 비교 전에 const key = e.key.toLowerCase() 한 줄. (e.code === 'KeyN'은 비QWERTY 배열에서 다르게 동작하므로 권하지 않습니다.)

2.5 로컬 DB가 손상된 상태의 "지금 동기화"가 원격 캘린더를 지운다

src/main/ipc-handlers.ts:403 (CalDAV) · :534 (Google) · src/main/caldav/sync.ts:324

데이터 파일을 못 읽으면 세션이 읽기 전용으로 내려가고 data는 빈 기본값이 됩니다. 그런데 getTasks()에는 assertWritable() 가드가 없어서(읽기는 무료 채널이라 의도된 것) []를 돌려줍니다. calendar-config.json은 별도 파일이라 멀쩡히 로드되므로 syncState에는 이전에 올린 모든 항목이 남아 있습니다.

src/main/caldav/sync.ts — planSync 마지막 루프 (코드 확인) for (const [taskId, entry] of Object.entries(state)) { if (seen.has(taskId)) continue plan.deletes.push({ taskId, href: entry.href, etag: entry.etag }) } tasks = [] 이면 seen 은 공백 → state 의 모든 항목이 DELETE 대상

로컬 데이터가 이미 읽히지 않는 바로 그 순간에, 마지막 남은 사본인 캘린더가 지워집니다. 서버 삭제는 앱에서 되돌릴 수 없고, 비워진 state가 저장되면서 무엇을 지웠는지 기록도 사라집니다.

이 프로젝트는 같은 위험을 이미 인지하고 있습니다 — databaseReadOnly.test.ts가 "빈 백업으로 진짜 백업을 덮지 않는다"며 exportData()가 읽기 전용에서 던지도록 못박아 두었습니다. 동기화 채널 두 개만 같은 가드를 못 받았고, isDatabaseReadOnly()는 export되어 있으나 자기 테스트 말고는 부르는 곳이 없습니다.

고치기: 두 sync-now 핸들러에서 runSync 전에 isDatabaseReadOnly()를 확인해 거절합니다. 방어적으로 planSync도 tasks가 비었는데 state가 비지 않았으면 삭제 루프를 건너뛰어야 합니다.

2.6 macOS Cmd+Q는 DB를 플러시하지 않는다

src/main/index.ts:252-264

closeDatabase()를 부르는 프로덕션 코드는 app.on('window-all-closed') 한 곳뿐입니다. Electron 문서가 명시하듯 Cmd+Q로 종료할 때 이 이벤트는 발화하지 않습니다(before-quit → 창 닫기 → will-quit 순서). 바로 아래 will-quit 핸들러는 리마인더 인터벌·라이선스 타이머·단축키만 정리하고 플러시는 하지 않습니다.

저장은 300ms 디바운스이고 쓰기 실패 시 최대 30초까지 재시도 대기열에 머뭅니다. 그동안 IPC는 렌더러에 이미 "성공"이라고 답한 상태입니다. database.ts의 주석은 closeDatabase()의 반환값을 "main/index.ts의 will-quit이 판정에 쓴다"고 설명하지만, will-quit은 그것을 부르지 않고 window-all-closed는 반환값을 버립니다.

고치기: before-quit(또는 기존 will-quit)에서도 closeDatabase()를 부르고 그 판정을 실제로 씁니다. window-all-closed 쪽은 Windows/Linux 경로를 위해 남겨 둡니다.

2.7 목록 드래그 재정렬이 전혀 동작하지 않는다

src/renderer/src/components/tasks/TaskItem.tsx:79

드래그 시작에서 effectAllowed = 'copy'를 설정하는데, 받는 쪽은 전부 dropEffect = 'move'를 요구합니다. HTML5 DnD 규격상 이 조합은 드롭이 허용되지 않아 drop 이벤트가 발화하지 않습니다.

코드 확인 — 저장소 전체에서 'copy'는 이 한 곳뿐 TaskItem.tsx:79 effectAllowed = 'copy' ← 유일 TimeBlock.tsx:55 effectAllowed = 'move' CalendarView.tsx:146 effectAllowed = 'move' UnscheduledRail.tsx:79 effectAllowed = 'move' KanbanView.tsx:77 effectAllowed = 'move' utils/dnd.ts:4 (자체 주석) "TASK_ID: 할일 목록 → 주·일 캘린더로 드래그(시간 배정). effectAllowed: move"

코드가 자기 문서화된 계약을 스스로 어깁니다. 행이 흐려지며 드래그는 시작되므로, 사용자에게는 "기능이 없다"가 아니라 "앱이 드롭을 놓쳤다"로 보입니다.

고치기: 'move'로 바꾸는 한 글자.

3. 나머지 결함 — 재현하고 고친 것들

서브시스템 14개를 병렬로 훑어 65건을 모았고, 2장의 7건을 먼저 고친 뒤 나머지를 건별로 재현·수정했습니다. 아래 표의 모든 항목은 수정됐고, 각 항목마다 수정을 되돌리면 깨지는 회귀 테스트가 붙어 있습니다.

처음 이 보고서는 "이 65건을 그대로 믿지 마십시오 — 통과율 96%는 검증이 충분히 적대적이지 않았다는 뜻"이라고 적었습니다. 그래서 전부 다시 검증했습니다. 건별로 에이전트 하나를 붙여 고치기 전에 실패하는 테스트를 쓰게 했고, 실패 출력을 실제로 받아 확인했습니다.

결과: 55건 중 53건은 재현됐고 2건은 결함이 아니었습니다(하나는 제가 이미 고쳐 둔 것, 하나는 같은 작업의 다른 수정이 이미 해결해 적용하면 오히려 회귀). 재현된 것 중 여러 건은 검증 과정에서 원래 제안된 수정이 틀렸다는 것까지 잡아냈습니다 — 예: Google 403을 전부 던지게 바꾸면 범위 밖 캘린더를 만난 사용자의 연동이 영구히 막힙니다. 그래서 상태 코드가 아니라 응답 본문의 reason으로 가르는 쪽으로 고쳤습니다.

7. 남은 한계 — 확인하지 못한 것

  • 실기기·실서버 조건은 여전히 못 봤습니다. 샌드박스(MAS) 빌드, 실제 iCloud·Google 서버 왕복, 알림 권한 승인 상태, 실제 라이선스 활성화, 다중 디스플레이는 검증 범위 밖입니다. 동기화 수정들은 서버 대역(fake) 위에서 검증했습니다 — 규격 해석이 맞다는 근거는 있지만 실서버 확인은 아닙니다.
  • 라이선스 enforcement는 꺼진 채로 테스트했습니다(IS_ENFORCED = false, 의도된 출하 상태). 라이선스 수정 3건은 단위 테스트로만 검증됐고, 켰을 때의 실제 동작은 확인하지 않았습니다.
  • 중간 커밋 일부는 단독으로 빌드되지 않습니다. 수정 38건을 병렬로 적용하면서 여러 건이 같은 파일(useStore.ts·ipc-handlers.ts 등)을 건드렸고, 먼저 커밋된 쪽이 옆 수정의 변경을 함께 안고 갔습니다. 브랜치 끝은 전부 초록이지만 중간 지점을 bisect하면 깨질 수 있습니다.
  • 이미 고아가 된 데이터는 치료하지 않습니다. 휴지통 하위작업 버그로 이미 보이지 않게 된 행이 기존 사용자 파일에 있다면 그대로 남습니다 — 수정은 새로 생기는 것만 막습니다.
  • lint 경고 11건이 남아 있습니다(errors 0). 기존 8건 + 새 테스트의 스타일 경고 3건으로, 저장소가 원래 경고를 안고 출하하고 있어 게이트로 보지 않았습니다.

8. 작업 중 생긴 일 — 실제 사용자 데이터

서브에이전트 하나가 격리 플래그 없이 앱을 띄워 실제 프로필을 열었습니다 (~/Library/Application Support/ticktick). 데이터 유실은 없었습니다 — 할일 27건의 ID가 9월 16일 백업과 정확히 일치하고, 앱이 자기 보호 백업(backup-before-greenday-2/)까지 만들어 뒀습니다.
