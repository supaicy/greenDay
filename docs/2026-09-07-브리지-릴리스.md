# 브리지 릴리스 — v1.5.0(옛 ID)에서 v2.0.0(새 ID)로

번들 ID를 `com.haru.app`(배포된 v1.4.1) → `com.begreen.greenday`로 바꾸는 절차. docs/27의
codex 8단계 중 **3단계(브리지)와 6단계(새 앱 첫 실행)를 코드로** 옮긴 것이 이 저장소의
`src/main/migration/`이고, 이 문서는 **빌드·배포 순서와 업데이트 feed 분리**를 적는다.

## 두 빌드

| | 브리지 v1.5.0 | 새 앱 v2.0.0+ |
|---|---|---|
| 명령 | `npm run package:bridge` | `npm run release` / 태그 푸시(release.yml) |
| 설정 | `electron-builder.bridge.cjs` (기본 yml 을 읽어 필요한 칸만 바꾼 JS — `extends` 는 배열을 합쳐 스킴이 둘 들어갔다) | `electron-builder.yml` |
| appId | `com.haru.app` | `com.begreen.greenday` |
| 버전 | `extraMetadata.version: 1.5.0` (package.json 은 그대로 2.0.0) | package.json |
| 자산 이름 | `Greenday-1.5.0-bridge-<arch>.dmg` | `Greenday-<arch>.dmg` (사이트가 쓰는 고정 이름) |
| 런타임 플래그 | `BRIDGE_BUILD=1` → `__BRIDGE_BUILD__ = true` | false |
| 자체 업데이트 | **꺼짐** (`capabilities.isBridge`) | 켜짐 |
| feed 파일 | `latest-mac.yml` (`channel: latest`) | `greenday-mac.yml` (`channel: greenday`) |
| 업데이터 캐시 | `ticktick-updater` (옛 그대로) | `greenday-updater` |

**같이 바꾸지 않은 것** — package.json 의 `name`/`productName`(Electron 내부 앱 이름 `ticktick`).
Keychain 항목 `ticktick Safe Storage` 와 userData 경로가 이 이름을 따르므로, 두 앱이 **같은
폴더**를 본다. 그래서 데이터는 옮길 것이 없고, 위험은 Keychain ACL 하나다.

## 업데이트 feed 분리 — 왜, 어떻게

electron-updater(GitHub provider)의 동작(`node_modules/electron-updater/out/providers/GitHubProvider.js`):

1. `https://github.com/supaicy/greenDay/releases/latest` 를 따라가 **GitHub 이 "Latest" 로 표시한
   릴리스의 태그**를 얻는다(아톰 피드의 최신이 아니라 Latest 마크다).
2. 그 태그의 자산에서 `<channel>-mac.yml` 을 읽는다. `channel` 은 앱 안의 `app-update.yml`
   (electron-builder 가 publish 설정에서 만든다)에 적힌 값이고, 없으면 `latest`.
3. 그 파일이 없으면 `ERR_UPDATER_CHANNEL_FILE_NOT_FOUND` — 업데이트를 **제안하지 않는다.**

이 세 가지에서 분리가 나온다:

- **옛 앱(v1.4.1·v1.5.0)** 은 채널이 없어 `latest-mac.yml` 을 찾는다.
- **새 앱** 은 `channel: greenday` 라 `greenday-mac.yml` 을 찾고, 릴리스에도 그 이름으로 올라간다.
- 새 앱 릴리스(v2.0.0)가 Latest 가 돼도 거기에는 `latest-mac.yml` 이 없으므로 옛 앱은 그것을
  받지 않는다. **다른 번들 ID의 앱이 옛 자리에 앉는 일이 구조적으로 없다.**
- 반대로 브리지 v1.5.0 릴리스에는 `greenday-mac.yml` 이 없으므로 새 앱이 그것으로 "내려가는"
  일도 없다(어차피 버전 비교에서도 막힌다).

### 순서 (이 순서를 어기면 laggard 가 생긴다)

```
① v1.5.0 브리지를 supaicy/greenDay 에 올리고 Latest 로 표시  ← 옛 앱들이 이것을 받는다
② 2~4주 대기 (docs/27 5단계). latest-mac.yml 요청 수는 폴링이라 설치 수 추정에 쓰지 않는다
③ v2.0.0 을 같은 저장소에 올리고 Latest 로 표시 (release.yml 이 `gh release edit --latest` 를 한다)
```

③ 뒤로는 옛 앱이 `/releases/latest` 에서 v2.0.0 태그를 얻고 `latest-mac.yml` 을 못 찾아
**아무것도 받지 못한다** — 아직 v1.4.1 인 사람은 영영 v1.5.0 을 못 받는다. 그래서 ②의 대기가
있다. 이것을 없애고 싶으면 아래 "더 튼튼한 대안"이다.

### 더 튼튼한 대안 — 새 앱 릴리스를 다른 저장소로

BicMac 이 이미 쓰는 방식(`supaicy/BicMac-releases`). 새 앱의 `publish.repo` 를 예컨대
`greenday-releases` 로 두면 `supaicy/greenDay` 의 Latest 는 영원히 v1.5.0 이고, 언제 열든
v1.4.1 사용자는 브리지를 받는다. 바꿀 곳 세 군데:

1. `electron-builder.yml` `publish.repo: greenday-releases` (채널은 그대로 둬도 된다)
2. `.github/workflows/release.yml` — `gh release edit` 와 bump-cask 의 URL 저장소
3. begreen `site/build.ts` 의 `greenday.downloadURL`, README 의 릴리스 링크

이 문서 시점에는 **하지 않았다** — 저장소를 새로 만드는 것은 사람 몫이고, 사이트 주소가
같이 바뀐다. 채널 분리만으로도 "옛 앱이 새 앱을 받는" 사고는 막힌다.

## 브리지가 첫 실행에 하는 일 (`src/main/migration/bridge.ts`)

1. **무결성** — `ticktick-data.json`(과 `.bak`)이 파싱되는가. 판정만, 고치지 않는다.
2. **백업** — `<userData>/backup-before-greenday-2/` 에 데이터 파일·설정·첨부를 복사.
   스테이징 → rename 이라 반쪽이 남지 않고, **이미 있으면 절대 덮지 않는다.** 암호문은 암호문
   그대로다(평문화 없음).
3. **sentinel** — `safeStorage.encryptString('keycheck-v1')` 을 `keycheck.sentinel` 에.
4. **상태 파일** — `migration-state.json` 을 원자적으로(임시 → fsync → rename → 디렉터리 fsync).
5. **동시 실행** — `app.requestSingleInstanceLock()` 뒤에서만 돈다.
6. 안내 모달(문구: `docs/reports/2026-09-07-bridge-copy.md`). "나중에"는 3일 스누즈, 설정 → 버전에서 다시 열기.

평문 handoff 파일은 없다. 새 앱에 넘기는 것은 `migration-state.json`(버전·시각·경로)과
암호화된 sentinel 뿐이다.

## 새 앱이 첫 실행에 하는 일 (`src/main/migration/arrival.ts`)

```
다른 인스턴스 확인(single instance lock)
→ 저장 잠금 (database.holdSaves — IPC 등록 전이라 렌더러 mutation 도 못 낀다)
→ 백업 (브리지 것이 있으면 그것을 쓴다)
→ bridge marker 확인
→ [표식이 있거나 암호문이 있을 때만] Keychain 안내 대화상자 → sentinel 복호화
    ok        → 게이트 열림. 실제 비밀값은 평소처럼 각 모듈이 읽는다
    denied/unavailable/mismatch/corrupt/missing(+암호문 있음) → **보호 모드**
→ Google 재연결 판정 (잠겼거나 토큰이 안 읽히면)
→ 정상이면 "옛 haru.app 지워도 됩니다"
→ 상태 파일 기록 (completedAt)
→ 저장 시작 (releaseSaves) — finally 라 중간에 던져도 풀린다
```

**보호 모드**(`secrets-gate.ts`)의 뜻: 세 writer(`saveAiConfig`·`writeConfigFile`·
`writeGoogleConfig`)가 저장 직전에 **파일에 있던 암호문을 되살린다.** 읽지 못한 채 설정을
저장해도 `*_enc` 가 null 로 덮이지 않는다. 사용자가 새 값을 넣는 저장과 연결 해제(`clearSecret`)
는 막지 않는다. 다음 실행마다 sentinel 을 다시 재므로, 나중에 "항상 허용"을 누르면 그때 풀린다.
직접 풀고 싶으면 배너의 "다시 연결했습니다 — 보호 해제"가 새 sentinel 을 심고 연다.

첫 버전은 **DB 스키마를 바꾸지 않는다** — `arrival.ts` 는 `ticktick-data.json` 을 읽지도 쓰지도
않는다(테스트가 바이트 동일성을 본다). 옛 앱으로 되돌리는 길이 언제나 열려 있다.
