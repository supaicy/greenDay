웹 직판과 App Store를 나눠서 봤다. 아래 상태는 전부 오늘 직접 측정한 값이다 — 문서에 적혀 있던 것을 그대로 옮기지 않고, 인증서·URL·릴리스·플래그를 하나씩 다시 확인했다. 네 가지가 그 사이 바뀌어 있었다.

1. 웹 직판 결제는 되지만 판매는 성립하지 않는다

결제 인프라(토스 키·Paddle 승인)만 끝나면 돈은 받아진다. 결제 → 키 발급 → 메일 발송까지 배관은 다 있고 테스트도 붙어 있다. 그런데 그 상태로 팔면 고객이 산 것이 아무것도 아니게 된다. 셋이 막혀 있다.

1

산 키가 아무 일도 하지 않는다

src/main/licensing/service.ts:33
export const IS_ENFORCED = false

이게 false인 동안 앱은 라이선스를 요구하지 않는다. 미인증 상태가 앱 동작을 아무것도 바꾸지 않고, 트라이얼 시작일조차 기록되지 않는다.

이대로 팔면 돈을 낸 사람과 안 낸 사람이 완전히 같은 앱을 쓴다. 환불 사유가 되고, 나중에 켜면 "전에 산 사람"과 "그냥 쓰던 사람"을 구분하는 문제가 남는다.

꺼진 채로 출하한 것은 의도된 설계다 — 유료 전환이 재설계가 아니라 플래그 하나 + 서버 배포가 되도록 배관을 잠들여 뒀다. 켜는 시점은 "서버 배포가 끝나고 실거래로 활성화까지 확인한 뒤"라고 코드 주석이 못박고 있다.

2

앱을 받을 곳이 없다

pay.begreen.dev에 있는 페이지는 이것이 전부다:

/success키 전달
/recover키 재발송
/terms · /refund · /privacy · /contact법적 문서
다운로드없다

begreen.dev(최상위)는 아무 데도 안 간다 — routes에 pay.begreen.dev만 있다. 랜딩 페이지는 begreen/mockups/greenday.html에 목업으로만 있다.

구매자 동선이 끊긴다 결제하고 키를 받은 사람이 앱을 어디서 받는지 알 수 없다. 성공 화면도 "앱의 설정 ▸ 라이선스에 붙여넣으세요"라고만 하고, 그 앱을 어떻게 구하는지는 말하지 않는다.

제출을 막는 것

개인정보처리방침 URL이 404다 문서에는 "✅ 게시 완료 — HTTP 200 확인"으로 적혀 있는데 지금은 안 열린다. 저장소 이름이 haru → greenDay로 바뀌면서 GitHub Pages 주소가 옮겨졌다. 
옛 주소  https://supaicy.github.io/haru/privacy.html      → 404
새 주소  https://supaicy.github.io/greenDay/privacy.html  → 200
         https://supaicy.github.io/greenday/privacy.html  → 404  ← 소문자 d는 안 된다

Pages 경로는 저장소 이름을 그대로 쓰고, 저장소는 greenDay다. 대소문자가 맞아야 한다.

이 문서 스스로가 "첫 제출 반려의 자주 걸리는 지점" 1번으로 꼽아 둔 항목이다. 지원 URL·마케팅 URL도 같이 깨져 있어 전부 새 주소로 고쳐 커밋했다.

남은 콘솔 작업

  • App Store Connect 앱 레코드 생성macOS · 이름 Greenday · Bundle ID com.supaicy.haru · SKU는 아무 값

  • 스크린샷 6장 업로드이미 촬영돼 있다 — docs/app-store/screenshots/
  • App Privacy 설문답은 "No, we do not collect data" — 근거와 심사 노트 원문이 문서 4절에

  • Google OAuth 클라이언트캘린더 연동을 쓰려면 별도. calendar.app.created 범위라 심사 부담은 작다
빌드 명령이 문서와 다르다 문서 7절이 가리키는 npm run package:mas는 끝이 --config로 잘려 값이 비어 있다. npm run mas:build를 쓴다 — 그쪽이 preflight를 먼저 돌리고 universal로 빌드한다.

3. "준비 중" 화면 구현 완료

"결제가 실제로 불가능할 때는 미서비스 화면을, 연동되면 결제 화면을" — 맞는 판단이라 그대로 만들었다.

비활성 버튼 셋은 "준비 중"이 아니라 "고장"으로 읽힌다. 지금이 정확히 그 상태였다 — 토스 클라이언트 키 없음, Paddle·크립토 링크 없음.

열린 레일보이는 화면
하나도 없음제품명·소개 + "아직 판매를 시작하지 않았습니다". 결제 UI를 아예 안 그린다
일부만열린 것만 탭에 남는다. 닫힌 탭은 지운다 — 회색으로 남겨 두면 그 수단을 기다려야 하는지 알 수 없다
전부기존 결제 화면 그대로
같이 잡은 것 — 심사를 막을 뻔했다 법적 링크와 사업자 정보가 #shop 안에 있어서 준비 중 화면에서 통째로 사라졌다. 결제사 심사는 레일이 아직 안 열린 상태에서 이뤄지므로, 심사관이 보는 화면에 약관·환불·개인정보·연락처가 하나도 없었다. "Paddle이 이 넷에 닿는지를 본다"는 주석이 바로 위에 붙어 있었는데도 그랬다. #shop 밖으로 뺐다.

구현 중에 한 번 깨졌고 실측으로 잡았다 — 닫힌 레일을 버튼 라벨을 세우기 전에 지우면 $("#pay-toss").textContent = … 세 줄이 없는 요소를 건드려 던지고, 그러면 화면이 통째로 안 뜬다. 지우는 시점을 라벨 뒤로 옮겼다.

팔기 전에 정해야 할 것

아래 둘은 코드 문제가 아니라 결정이다. 정해지지 않으면 결제 인프라가 끝나도 팔 수 없다.

  • 다운로드를 어디서 주나랜딩 페이지를 세울 것인가(begreen.dev 최상위), 아니면 구매 완료 화면과 키 메일에 GitHub 릴리스 링크를 직접 걸 것인가. 후자가 훨씬 빠르지만 "제품 소개"가 없는 채로 파는 셈이 된다
  • IS_ENFORCED를 언제 켜나코드 주석의 조건은 "서버 배포가 끝나고 실거래로 활성화까지 확인한 뒤". 켜는 순간부터 트라이얼 시작일이 기록되므로, 켜기 전에 산 사람들은 별도로 챙겨야 한다
  • v2.0.1 Draft를 공개할 것인가지금 공개된 최신은 4월의 v1.4.1이다. 다운로드 경로를 만들기 전에 이것부터 정리해야 한다

순서에 대한 의견. 웹 직판과 App Store는 서로를 기다릴 필요가 없다. App Store 쪽은 개인정보방침 URL만 고치면 오늘 제출할 수 있는 상태이고(빌드 점검 5개 통과), 스토어 빌드는 capabilities가 라이선스를 강제하지 않으므로 IS_ENFORCED와 무관하게 나갈 수 있다. 웹 직판은 위의 셋을 푸는 데 시간이 더 걸린다.

이 문서의 근거. 인증서는 security find-identity, 프로파일은 security cms로 복호화해 만료·App ID를 읽었고, URL은 전부 curl로 상태 코드를 확인했다. 릴리스 상태는 gh release, 플래그는 소스 직접 확인이다.
